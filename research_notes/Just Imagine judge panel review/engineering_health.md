### Inferences

- The story failure probably happens like this. When one parallel `tx.get` is aborted for contention, the SDK rolls back the transaction while the sibling read is still in flight. That sibling read then receives INVALID_ARGUMENT, which the SDK does not retry. A double-tapped "make a story" could therefore return a 500 to one request instead of the idempotent result. Running the reads one after another, or catching and retrying, would likely fix it. This is PLAUSIBLE, not proven against production Firestore.
- The same transaction reads every story owned by the parent just to check `books.size >= limits.savedWorlds`. The cost grows with library size, and every story in the parent's library becomes part of the transaction's read set. A counter document or `count()` would scale better (READ).
- The e2e drift shows the uncommitted i18n change was not run against the browser suite before this audit. The test suite did its job. The work is unfinished.

### Gaps

- I did not run the story test against real Firestore, so whether the failure reproduces in production is unconfirmed.
