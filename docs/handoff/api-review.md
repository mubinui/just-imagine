# API security and correctness review

Scope: `services/api`, `firestore.rules`, current REST contracts, and design sections 10–12. Read-only implementation review; no tests were rerun. The report itself is the only file written.

## Findings

1. **High — deletion is neither durable nor fenced against concurrent writes.** `services/api/src/store.ts:172–187` removes a child and then performs one-time queries/deletes; `:189–204` does the same for accounts, leaving the user active until the very end. `services/api/src/app.ts:117–125` runs this work inside the HTTP request despite returning 202. There is no persisted deletion intent, worker retry, tombstone, or coordination with already admitted sessions/builds. A request/process failure after profile deletion leaves associated worlds/sessions indefinitely unless a caller manually retries. An account can create another child or start work during cleanup; a session/build admitted before deletion can write after the cleanup queries, recreating deleted data. This violates section 10's Cloud Tasks deletion within 24 hours. Persist a deletion job and mark the account/profile as deleting transactionally; have all admission and completion writers honor that state, then retry cleanup durably.

2. **High — account deletion cannot recover from failure at its final Auth step.** `services/api/src/store.ts:202–204` deletes the user document before `adminAuth().deleteUser(uid)`. If Auth fails transiently, the route returns an error with Auth still present. A retry immediately fails `store.me` in `services/api/src/app.ts:118` (and `this.user` at `store.ts:190`) because the user document is gone. There is no durable job to finish deleting the Auth identity. Keep a deletion record independent of the user document and make final cleanup idempotent, including an already absent Auth user.

3. **High — repeated/concurrent Checkout requests permit multiple billable subscriptions and incomplete cancellation.** `services/api/src/billing.ts:30–42` checks only the last webhook-populated subscription document and creates a new Checkout Session on every call, with no checkout claim, reusable pending session, or idempotency key. Two requests before either checkout webhook arrives both succeed; both sessions can become separate subscriptions. Webhooks then overwrite the single `subscriptions/{uid}` record (`:113–120`), and account deletion cancels only that one subscription (`:56–59`). The other subscription remains active, while its later deletion/update can also overwrite the plan derived from the still-active one. Serialize/reuse pending checkout and enforce one active provider subscription per customer; cancellation must reconcile all subscriptions, including completed checkouts whose webhooks have not yet reached Firestore. Add concurrency and webhook-delay coverage.

4. **Medium — webhook freshness is not reliably ordered for concurrent snapshots.** `services/api/src/billing.ts:81` retrieves provider state before the Firestore transaction; `:108–110` rejects only strictly older event timestamps, which have second resolution. For two same-second events, one handler can fetch an earlier active snapshot, pause, and commit after another handler has fetched and committed cancellation. Equal event timestamps allow the stale active snapshot to restore Family. The current duplicate-event test exercises only sequential identical events. Serialize reconciliation per subscription or use a reconciliation strategy that cannot commit an older fetched snapshot after newer state, and cover equal-timestamp concurrent events.

## Spec and quality verdict

**Changes required before release.** REST method/path coverage matches the current protocol, child payloads use strict schemas, profile limits are serialized transactionally, protected endpoints verify Firebase tokens, world/child reads enforce ownership, Stripe signatures and event-id transactions are present, and Firestore rules deny client writes while scoping reads to owners. No direct cross-parent read/write bypass was identified in these rules or route handlers.

Sections 10–12 are incomplete for the required durable deletion lifecycle. Billing has a payment lifecycle concurrency defect despite test-mode-only operation. The existing tests support basic route validation, ownership/rules enforcement, child creation concurrency, recursive cleanup in a quiescent database, and sequential webhook deduplication; they do not substantiate deletion under failure/in-flight writes, account deletion recovery, checkout concurrency, or webhook ordering. Unbounded list queries are an operational scaling concern rather than a current contract mismatch. Infrastructure-wide regional placement, least privilege, model moderation, and kill-switch enforcement are outside this API-only review.
