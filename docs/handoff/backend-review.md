# Backend review

Read-only code review of gateway/builder and API billing/deletion against spec sections 8–12 and current protocol. No tests run; no implementation files changed.

## Important findings

1. **P1 — Individual world deletion can be undone by an in-flight builder.** `services/api/src/store.ts:174–176` recursively deletes the world without installing a tombstone or coordinating with `worldLocks`. `services/builder/src/worker.ts:65–70` only checks its lease and account/child deletion locks before `tx.set` of the full world. Delete a world while its assets generate: the next publish recreates it. Fence world deletion in the same transaction read by all publishes and patch/version commits.

2. **P1 — Patch delivery is not idempotent after publication.** `services/builder/src/worker.ts:73–79` commits the patched world, then writes the version, and only later marks the job complete (`:56`). A version-write failure, completion failure, or worker termination after publish causes the same Cloud Task to run the patch again against the already patched scene. Increment/move/add patches can therefore apply twice; an unlucky retry can corrupt the intended result. Atomically commit the patch, version, and durable applied job marker under the lease, and make retries recognize it.

3. **P1 — Unbounded socket work queues bypass timely quota/pacing enforcement and consume memory/model calls.** `services/gateway/src/gateway.ts:14,94,110`: every valid control frame appends a promise; text moderation and character handoffs run serially, and quota/pacing timers append to that same queue. An authenticated client can send thousands of valid small text frames, keeping the audio relay live while the meter/end action waits behind minutes of moderation requests. `maxPayload` limits only individual messages. Bound outstanding controls, rate-limit expensive actions/audio, and run quota/session-deadline shutdown independently of queued user work.

4. **P1 — Session cleanup skips finish on metering failure and can reject without a handler.** `services/gateway/src/gateway.ts:16–20` awaits `meter()` before `finish()` in one try; a lost lease, deletion fence, Firestore failure, or usage write failure skips summary/finish entirely. `ended` is already true, so the serial catch calling end again cannot repair it. The disconnect/grace paths call `void end(...)` without catch, allowing an ordinary backend failure to become an unhandled rejection (and potentially terminate Node). Ensure shutdown always attempts fenced finish/release independently of metering, and handle all detached shutdown promises.

5. **P1 — Account deletion fences do not cover writes after the deletion sweep.** `services/gateway/src/store.ts:30–39` checks deletion locks in its session transaction, then separately calls `addVoiceSeconds`; `services/builder/src/worker.ts:97` separately calls `addImages`. Both write `usageDaily` through an unfenced transaction in `packages/server-core/src/quota.ts`. Account deletion can fence and delete usage between these operations, after which the delayed writer recreates the deleted account's usage document. `worker.ts:79` also creates a version subdocument outside the publish fence; deletion between publish and version write leaves an orphan world version after recursive deletion. Include deletion fence reads in every relevant commit, and atomically fence version writes with the world.

6. **P1 — Billing portal customer creation bypasses the billing lease used by deletion.** `services/api/src/billing.ts:41` calls `customer()` outside `serialized()`. A portal request can pass the deletion-lock check, pause during Stripe customer creation, and overlap account deletion's serialized cancellation. Cancellation sees no persisted customer and returns; the portal request then persists the new customer and creates a portal session after deletion began. The check in `customer()` is only a preflight read. Serialize portal/customer initialization with cancellation and transactionally check the deletion fence when persisting the customer.

7. **P2 — Gateway metering is split into two non-idempotent writes.** `services/gateway/src/store.ts:30–39` increments session voiceSeconds/renews its lock, then increments daily usage. If the second operation fails after the first commits, the session total and daily usage diverge. The final-meter retry can duplicate session seconds because `lastMeter` advances only after the whole store call succeeds (`gateway.ts:15`). Use a single transaction for both records or a durable monotonic metering checkpoint that makes retries idempotent.

8. **P2 — Builder failure does not publish a failed world milestone.** `services/builder/src/worker.ts:58–61` only marks builderJobs failed and releases the lock. A failure before the first publish produces no observable world document; a failure after publication leaves status building. Gateway watches only world status (`services/gateway/src/gateway.ts:49–53`), so its failed notification path never receives these failures. Publish a fenced failed state for terminal failures and distinguish retryable attempts from final task exhaustion.

## Scope limits

No real Vertex/Stripe/Cloud Tasks calls, emulator tests, or runtime load tests were performed. The builder's convex-only collider limitation is already disclosed in backend-report.md and was not duplicated here.

## Scoped re-review after fixes

Reviewed the eight original findings and directly introduced lifecycle behavior. No tests run and no implementation edits made. Original findings 1, 2, 5, 6, and 7 have their concrete reported races addressed: world tombstones fence publications, patch/version/job completion commit atomically, daily usage reads the account deletion fence, portal initialization uses the billing lease with fenced persistence, and voice metering uses an atomic monotonic checkpoint. The metering-failure branch in finding 4 now attempts finish and catches rejection. Finding 3 now bounds controls and runs metering/end independently.

Two important issues remain:

1. **P1 — Independent shutdown can install listeners after cleanup (introduced by the queue fix).** `services/gateway/src/gateway.ts:65` awaits enqueue, then unconditionally installs the world and builder-job listeners. `end()` at `:21–24` now executes independently of that running control operation. Reproduction: hold enqueue pending, send client end (or trigger the quota deadline), let end finish/unsubscribe/remove its session, then resolve enqueue. `watch()` installs new listeners after the only cleanup has already run; both closures retain the ended session indefinitely. Add an ended/generation guard after awaited work before installing listeners, and make watch itself refuse ended sessions. Apply equivalent guards to handoff after its summary await so an ended session does not open a new upstream connection.

2. **P2 — Original finding 8 is only partially fixed: pre-claim build failures still have no observable failure record.** `services/builder/src/worker.ts:15–34` performs kill-switch checking and lease/quota/ownership claiming before the try/catch beginning at `:36`. A normal saved-world-limit rejection (`:29`) happens before builderJobs is created; no world exists either. Gateway has already sent queued and subscribes to those two absent documents, so it never reports failure, even after Cloud Tasks retries exhaust. Record permanent admission failures durably by job ID (without overriding an active lease/complete job), or reject them before acknowledging enqueue. Preserve retryable contention separately. The new failure watches correctly cover errors that occur after a successful claim.

The added finish transaction's active-session guard makes repeat finish calls avoid incrementing child progress twice. No new blocking issue found in that transaction during this scoped pass.
