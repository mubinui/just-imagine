## Important findings

1. **P2 — A failed patch poisons the world status, and a successful retry never repairs it.** `services/builder/src/worker.ts:235–246` marks the existing world `failed` for every post-claim exception, including a transient patch model failure. On the next successful delivery, `patch()` reads that failed world and spreads it into the atomic write at `:301–310`, retaining `status: 'failed'` even though the job becomes complete. Trigger: begin with a ready world, fail the first patch generation, then succeed on retry. The saved world and gateway continue reporting failure. Preserve the last playable world's status on patch failure and track the failed job separately, or restore ready on successful patch. Related notification gap: `services/gateway/src/gateway.ts:328–346` does not attach a watch for the patch job; `:272` deduplicates solely by milestone. Normal ready-to-ready patches therefore never send completion to Live, and pre-claim patch failures are invisible. Observe the patch job and key milestone deduplication by job/world revision as appropriate. A focused regression should assert both stored status and failed/successful patch notifications.

2. **P2 — Live receives no usable manifest of generated world controls.** `services/gateway/src/gateway.ts:275–277` sends only title and milestone; build/patch tools return only job IDs. `services/gateway/src/live.ts` supplies no world document/control manifest in its initial instructions, and no tool can inspect one. Yet `set_variable`, `start_challenge`, material dials and targeted spells validate exact generated keys (`gateway.ts:348–422`). Trigger: open a generated Lab whose variable/challenge IDs are arbitrary, then ask the character to adjust a variable or start its challenge. The model must guess identifiers it has never received, so valid control actions cannot be performed reliably. Supply a bounded validated manifest (concepts, available dials/material keys, variable names/ranges, challenge IDs/goals, useful tags) when a world becomes available and after patches. Replay it after opening/reopening Live: the saved-world watcher is installed before `await openLive` at `:584–585`, so its initial callback can currently discard even the title while `session.live` is absent.

3. **P2 — Initial upstream connection can install an interval after session cleanup.** `services/gateway/src/gateway.ts:585–612` unconditionally assigns the meter timer after awaiting `openLive(s)`. Trigger: hold the first provider `open()` pending, send client end (or let disconnected-session grace expire), wait for `end()` to clean up, then resolve the provider. `openLive` correctly closes the stale connection, but hello continues and creates a permanent interval whose callback returns early because `s.ended` is true. It retains the session after the one cleanup already ran. Add an ended/socket-generation guard before installing the interval; cover delayed initial open plus terminal shutdown. This is the same lifecycle pattern as the already-fixed late watch installation, in a different still-open continuation.

4. **P2 — Scene validation fallback is reported as an ordinary successful generation.** `services/builder/src/worker.ts:121–128` catches two failed scene attempts and substitutes a curated fixture, but `:218–227` publishes ready, marks the job complete and emits `builder_result success:true`. Only a server log distinguishes the substitution. The gateway tells the child the replacement world is ready without explaining the failed request or offering the fallback; Terraform's builder-failure ratio also counts these failures as successes. Trigger: make the scene model return invalid scenes twice. The design spec's failure-mode table (line 663) explicitly requires the failed job/character explanation and an offered nearest-concept fallback. Retain a durable explicit fallback/failure outcome and tell the gateway why the world differs; ensure generation-failure metrics count it even when the curated fixture remains playable. Current fallback validation and tier filtering are sound; the missing piece is the cross-component outcome.

## Scoped fix re-review — 2026-10-15

Reviewed only the four findings and their corrective source/regressions. No application edits or test reruns. The controller reports 12 gateway tests and 14 builder unit tests passing; final emulator/workspace verification remains controller-owned.

1. **Patch state and notifications: fixed by source inspection.** The worker marks the world failed only for build jobs; successful patch commits explicitly set ready. The existing emulator patch test now first rejects generation, asserts that the old world remains ready, retries successfully, and verifies idempotency. Gateway patch requests replace the job watch, filter stale world job IDs and deduplicate on job ID plus milestone. The added gateway regression exercises a ready-to-ready patch announcement.
2. **Live control manifest: fixed by source inspection.** World updates cache a validated-data manifest containing concepts, dials, material keys, variables, challenges and entity tags. It is sent immediately when Live exists and replayed after a successful open, covering the original saved-world callback-before-open race and character handoffs. The new regression asserts variable/challenge identifiers reach Live and the patched title is announced.
3. **Post-cleanup timer: fixed by source inspection and focused regression source.** Hello returns when the session ended during initial open before installing its interval. The regression holds provider open, ends the session, releases it and asserts no meter interval was installed.
4. **Fallback outcome: primary failure reporting fixed; replay edge remains.** The worker persists terminal `fallback`, treats redelivery as already complete and emits `builder_result success:false` with a fallback milestone. The gateway job watch tells the current Live connection that a safe sample replaced the failed request and offers exploring it or trying again. However, that explanation is not included in cached `worldContext`; a later handoff/reopen replays only ordinary ready-world context. Opening the saved sample in a new session invokes `watch` without a job ID and never reads its durable fallback outcome. This continuation was reported to the controller: include the outcome in replayed context and observe the current world's job outcome when reopening a saved world. The reported original hidden-failure metric is resolved.

The re-review establishes source closure of findings 1–3 and the principal worker/active-session correction for finding 4. It does not substitute for real model, cloud, device or full workspace verification.

### Fallback continuation re-review

The fallback replay gap is now closed by source inspection: `watch()` observes the current world's durable job even when hello did not supply a job ID, combines the outcome and control manifest into `session.worldContext`, and the existing Live-open path replays that combined context. Builder fallback remains terminal/idempotent. The queued build's `conversationSummary` now uses a deterministic age/tier/concept brief; the inspected job constructor no longer copies transcript excerpts into Cloud Tasks payloads. This is a targeted source claim, not a broader assertion that generated request descriptions can never contain personal information.

One directly introduced cache edge was reported to the controller: the job callback currently ignores `running`/`complete`, so after a failed attempt successfully retries under the same job ID, cached `outcome` still says "World building failed" alongside the ready manifest and survives handoff. Clear a prior failure outcome when the durable job resumes or completes; retain terminal fallback explanations. No other material residual was established within this narrowly reviewed change.
