## Behavior

- Sikhi uses a short header, a clear invitation and one scrolling region for the six compact island destinations and Katha's story room. Desktop uses three columns, phone two. The dock stays separate, ring geometry has real headroom, Bangla labels retain readable leading, and challenge progress is explicitly distinct from played chapters. Loading no longer substitutes demo points; failed progress can be retried and state belongs to the current explorer.
- App default, Forest, Ocean and Terracotta are available from ordinary app headers and parent Settings. A separate device preference survives polling, reloads and cross-tab changes; unavailable storage permits a visit-only choice. The operator's audited publication remains the shared default. Resolved tokens, branding and browser assets change together; character/world artwork stays original. Fullscreen child routes hide the underlying shared header's duplicate controls.
- Voice selection retains the latest character and world during token acquisition, initial connection and reconnection. Creative turns wait for the selected context, and rejected selection discards a pending turn instead of applying it to the old game. Handoffs invalidate old callbacks immediately, stop stale audio/mic/tool forwarding, restore the correct speaker and tolerate summary failure. The six authored character voice configurations are used individually.
- The teacher leaderboard has one school/class selector beside its time-period group. A chosen class always requests that class, with no redundant disabled scope pills. Results filters and tables have explicit loading/error/empty states and do not retain another selection's stale data. Question labels show quiz/practice ordinals and current public wording rather than internal IDs; historical grading and completion are unchanged.
- Teacher/operator text fields offer collapsed AI writing help for titles, explanations, instructions, lab goals, questions, options and hints, including unsaved/new lessons. The current language, text and lesson context produce a validated plain-text proposal. Apply/Discard is explicit; changed source/language/context blocks stale application. Applying preserves the other language and science/key data, clears both language approvals and never saves or publishes automatically. Question wording and answer keys still need teacher review together. Whole-lesson drafting/translation is visible near the editor top and remains save-gated.
